# 20260411

Running mmproj on the CPU causes conversations involving image recognition to stall until the CPU finishes its single-threaded computation, at which point GPU inference resumes. This is very slow.

New finding: even with only 23 layers fitting on the GPU, the MoE architecture does not need to compute with all the weights on each inference step, unlike a dense model. This keeps the CPU workload relatively light, allowing an initial speed of 35 t/s.

To prevent the system from freezing, avoid filling VRAM completely. For example, loading 24 layers uses 23.7 GB out of just 23.98 GB of total VRAM.
Since this is the only GPU, other system components—even something as simple as a notification—can exhaust the remaining VRAM and trigger swapping.
This works similarly to RAM swapping, but VRAM swapping transfers data to and from system RAM over PCIe, which is very slow. Loading 23 layers instead of 24 leaves some headroom and is more stable.

Testing showed that both Q8_0 and Q6_K are reluctant to call tools. Even with guidance in the system prompt such as “You may call tools” and “There are no restrictions on tool use,” they still tell the user “I don't know” instead of searching when faced with an unfamiliar question. However, a negatively worded instruction such as “Do not answer the user with ‘I don't know.’ If you don't know, call the search tool” makes the model proactively call tools when asked again.

Q5_K_M fits entirely in VRAM, with no obvious drop in conversation quality, but adherence to the system prompt is somewhat worse. Like the previous two quantizations, it sometimes skips thinking and goes straight to the answer.

KV cache quantization does not speed up computation; it actually slows it down because types unsupported by the GPU must be converted back to BF16 or F16. There are also memory leaks with the KV cache at this stage, so I recommend avoiding KV cache quantization.

Q8_0 quantization is a reasonable choice for the 26B A4B model. Thanks to its MoE architecture, the speed is quite good.

After reviewing Gemma 4's sampling parameters again, the official temperature, topP, and topK settings should be left unchanged. Other sampling settings, such as penalties, should also be disabled (`--repeat_penalty 1.0 --min-p 0`).
To avoid interference from newly added parameters, it is better to remove the extra samplers outright rather than disable their settings individually.

Use the system prompt to steer the model toward more exploratory or more definite responses.

I also found https://github.com/ggml-org/llama.cpp/issues/11681
  + `--ctx-size` is actually the KV cache size. Each slot's context size is `c / parallel`.
  + `-c 262144 --parallel 2` gives each request a 128K context.
  + To process two requests simultaneously with 256K each, you need to set `-c` to 512K.

I do not have that much VRAM, so I set `parallel` to 1.

Enabling `--kv-unified` lets multiple slots share the KV cache, but exceeding the total context size across those slots seems to cause an immediate error.

A reminder for my future self: using BF16 for the KV cache does not improve the model's output.
