# 20260411

The Q8_0 weights take up 32 GB, so they definitely will not fit in 24 GB of VRAM. That leaves 8 GB on the CPU, and this is a dense model too—I dread to think how slow it will be.

64K context:
+ Q8_0, 31 layers loaded on the GPU: initial inference speed of 4.2 t/s, dropping to 3.4 t/s after one conversation turn (one tool call).
+ Q6_K, 39 layers loaded on the GPU: initial inference speed of 5.6 t/s, dropping to 5 t/s after one conversation turn (one tool call).
+ Q5_K_M, 42 layers loaded on the GPU: initial inference speed of 7.2 t/s, dropping to 6.4 t/s after one conversation turn (one tool call).
+ Q5_K_S, 44 layers loaded on the GPU: initial inference speed of 8.6 t/s, dropping to 7.2 t/s after one conversation turn (one tool call).

With Q8 quantization, nearly half of the 61 layers must run on the CPU, making it very slow. Q6_K is only marginally better.

Changing the batch size from the default of 2048 to 512 (https://mintlify.wiki/ggml-org/llama.cpp/advanced/performance-tuning#platform-specific-tips)
showed no noticeable improvement in VRAM usage or inference speed during testing.

# 20260418

The second GPU arrived, so there is now plenty of VRAM. However, fitting the entire Q6_K model on the GPUs with little or no reduction in context size requires a smaller ubatch.
With ubatch set to 32, pp is only a little over 100 t/s, which is completely unusable for long inputs (208K context). So I had to drop down to Q5_K_M.

The current configuration achieves pp of 280 t/s and tg of 14 t/s (actual context close to 200K: the three Sayaka Saeki novels plus one round of questions and answers).

Gemma 4's KV cache optimization is still somewhat lacking. The model itself is smaller than the 26B model, but its greater number of layers makes the KV cache much larger.

# 20260419

Watch out for out-of-memory errors: a single Gemma 4 context checkpoint takes up 1 GB, and llama-server allows 32 checkpoints by default. No wonder it keeps running out of memory.

211K context test:
 kvo: pp 288.05 t/s, tg 14.26 t/s
nkvo: pp had already fallen below 140 t/s at around 57% completion, so I stopped the test. Started a new conversation and sent “Hello”: tg 9.1 t/s.

With nkvo, increasing ub is still slow.
Using `ctk f16 ctv q8_0` requires a custom build; otherwise, computation can only run on the CPU.
Setting both to `q8_0` allows GPU computation without recompiling, but affects output quality. Also, non-f16 KV caches seem to cause memory leaks on ROCm.
