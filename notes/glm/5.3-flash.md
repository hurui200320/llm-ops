# 20261105 GLM-5.3-Flash IQ2_S on maya: speed tuning (pp/tg)

Model/lane: `glm-5.3-flash-iq2s-derisked` (Maya-M-Derisked IQ2_S, 116 GB, 3 shards) on the Maya GLM engine
(`maya` 1.1.53, HIP/gfx1100), 2x RX 7900 XTX. Bring-up and deployment record: [notes/maya.md](../maya.md)
20261105. This is the deferred tuning pass: raise pp/tg while keeping **fp16 KV, 512k context** and the
headroom target **>=500 MiB free on the monitor GPU (HIP CUDA0 / sysfs `card1`) and >=300 MiB on the other
(CUDA1 / sysfs `card0`) while inferencing** (not at load; the engine's buffers grow with the first request,
and the monitor card also carries the desktop).

## Method

- One-shot arm containers on an isolated copy of the lane tree
  (`/mnt/unenc-xfs/maya/glm53f-iq2s-derisked-tune`; the production shards stay read-only per-file binds, the
  pack/vision are a copy, slots wiped). One config JSON per arm under
  `/mnt/unenc-xfs/maya/tune/glm-arm-configs/<arm>/`; the repo entrypoint mounts it as `/repo-configs-glm`.
  Port 10110, GPUs exclusive (llama-swap stopped for the tuning window).
- Speed: `bench/speed/run_longctx.py --model glm-5.3-flash-iq2s-derisked --ctx 524288 --in-pcts 40,85
  --out-pct 1` directly on the container (1 rep screening, 2 reps confirmation). maya has `/tokenize`, so a
  ladder pays no calibration prefill. `cache_n 0` on every measured rep (bench-checked).
- 5 s sampler over `/sys/class/drm/card*/device/mem_info_vram_used` (card1 = monitor/CUDA0, card0 = other/
  CUDA1), `MemAvailable`, `SwapFree` for the whole run.
- Engine placement lines (split prediction, pools, chunk borrow, KV, MTP) captured per arm from
  `/opt/maya/maya-glm53f-iq2s-derisked-hip.log`.
- Knob hygiene: one knob per arm on top of A0 unless stated; the box drifts (page cache), so controls are
  re-run next to any small delta. Bit-exact knobs first; answers-changing knobs are not part of this pass.

Placement: auto split **CUDA0 [0,24) / CUDA1 [24,45)+head+MTP** (predicted 60.4 ms/token; CUDA0 57.9,
CUDA1 60.4, pipelined decode costs the slower part). Expert pools 16.40 + 16.50 GB = **4,034 experts
(2,029 + 2,005), 59 % of the routed ones**; RAM tier 17.57 + 18.41 GB (2,178 + 2,245 slots, 8,308 experts
warm in ~13 s); CPU lane 8 threads a card, the x4 card's PCIe expert 1.230 ms vs 0.175 ms on the CPU (it
takes up to 7 of 8 RAM-tier experts on the CPU). Chunk **8192**, borrowing 2,659 MB (activations 2,444,
scratch 96, staging 103). KV streaming 32,768 of 524,288 positions of each of 6 DSA layers in VRAM
(0.20 GB) + 3.22 GB pinned a card. Dense weights 3.53 / 3.32 GB, state/KV at 512k 0.69 / 0.68 GB.
MTP: NextN block (blk.45) 173 MB dense on CUDA1, drafts over 98,741 of 154,880 tokens.

|---|---:|---:|---:|---:|---:|
| A0, 40 % (209K) | 748.0 | 16.90 | 0.776 | - | - |
| A0, 85 % (446K) | 740.0 | 15.80 | 0.773 | - | - |
| whole run | - | - | - | **2,244 MiB** | **2,716 MiB** |

`MemAvailable` min 11.7 GiB, swap flat (72.6 GiB free). The lane is **over-reserved**: `RESERVE_MB=3072`
leaves ~2.2-2.7 GiB free during inference against the 500/300 MiB target, so the reserve finalization arm
can claw back expert room later (per-card, via `RESERVE_LATER_MB`). tg is the weak axis (16 t/s vs the
AGENTS.md 25), pp is ~750 at both levels (flat across context, as on the DS4 lane).

### Decode and prefill mechanics (A0 engine stats)

Decode is **fetch-bound, not compute-bound**: `glm stat: decode 59-66 ms/tok | vram hit 66-68 % | ram
fetches 14-16/tok | disk 16-18 reads/tok in 11-13 waits/tok, **33-37 ms/tok** | promotions 25-29/tok |
cpu lane 91-96 experts/tok in 33-34 ms/tok`. The RAM tier holds 4,423 slots of the ~8,000 off-VRAM
experts; the rest stream from the SSD (~2 ms a read). A kernel-only change cannot move tg much here.

Prefill is **split-bound**: 40 % `147,456 tokens in 175.8 s (839 tok/s), 18 chunks of 8192 | CUDA0
127.8 s, CUDA1 168.7 s`; 85 % `393,216 tokens in 494.3 s (795 tok/s), 48 chunks | CUDA0 393.9 s, CUDA1
484.3 s`. The x4 card is 23-32 % slower a stage than the monitor card, so the auto split (`[0,24)`
CUDA0 / `[24,45)` CUDA1) is not stage-balanced, whatever its predicted 60.4 ms/token says.


The knob reached the dispatch - the engine logged `glm experts: CUDA0/CUDA1 IQ2_S gate/up on the tuned
RDNA kernel (token path)` - but pp/tg are unchanged:

| level | pp t/s | tg t/s | accept |
|---|---:|---:|---:|
| A1, 40 % | 749.9 | 16.90 | 0.753 |
| A1, 85 % | 738.5 | 15.10 | 0.755 |
| A0, same levels | 748.0 / 740.0 | 16.90 / 15.80 | 0.776 / 0.773 |

Upstream measured 1.34-1.43x for this kernel on the same GPU, but only on the expert kernel itself; here
the token time is 33-37 ms of disk wait + a 33 ms CPU lane, so a faster gate/up GEMM on the ~66 % of
experts that are in VRAM is dilution. The 85 % tg delta is acceptance/content (0.755 vs 0.773), not the
kernel (bit-exact). **Not kept**: it buys nothing measurable, and it is one more knob to carry.

## Reorder: headroom before compute (user direction)

The A0/A1 stats showed the decode is bound by expert fetches (~33-37 ms of a 59-66 ms token is disk wait;
the CPU lane carries 91-96 experts a token), so compute knobs cannot be measured cleanly until the expert
tiers are as large as the headroom target allows. The pass was reordered: **VRAM reserve first**, then
re-run A1 and the rest on the new base. A preliminary split screen (aborted after two arms when the
reorder was agreed) is kept as a data point only: `SPLIT=27` at reserve 3072 measured pp 822.6 / tg 16.60
at 40 % (A0: 748.0 / 16.90), i.e. moving layers off the x4 card helped pp even before the reserve change;
re-tested properly later.

## A4 - layer split sweep at reserve 1500/700: auto (24/21) stays

`MAYA_GLM_SPLIT=K` (K = CUDA0's layer count; CUDA1 takes `[K,45)`+head+MTP). 40 % level, 1 rep, then an
interleaved 52K decode probe (4 x 256 cached decodes, alternating with the control) because the ladder tg
swings +-5 % session to session while pp reproduces within 0.2 %.

| `SPLIT` | layers CUDA0/CUDA1 | pp 40 % | tg ladder | **tg52 probe** | experts in VRAM |
|---|---|---:|---:|---:|---:|
| **24 (auto, control)** | [0,24) / [24,45) | **774.8** | 19.4 | **24.57 / 25.43 / 24.83 / 23.62** | 4,517 |
| 25 | [0,25) / [25,45) | 802.7 | 17.9 | 22.00 | 4,503 |
| 26 | [0,26) / [26,45) | 834.1 | 18.1 | 22.85 | 4,499 |
| 27 | [0,27) / [27,45) | 860.9 / 864.4 | 17.8 / 18.2 | 21.90 / 21.70 | 4,497 |
| 28 | [0,28) / [28,45) | 843.9 | 16.1 | - | 4,493 |
| 29 | [0,29) / [29,45) | 838.8 / 840.2 | 16.3 / 17.2 | - | 4,488 |

Two effects, both real:

- **pp**: moving layers off the x4 card is worth up to **+11.6 %** (K27). The prefill stage line explains
  it: at auto the x4 card's copy lane streams its chunk's experts at **6.3 GB/s** against the monitor
  card's 16.3 GB/s, so CUDA1's prefill stage (168.7 s) is the makespan against CUDA0's 127.8 s. Every
  layer moved off CUDA1 shrinks that stage. The curve peaks at 27 and falls by 29 (CUDA0's own stage
  becomes the limit).
- **tg**: any K != 24 costs **6-13 %** of decode at 52K, because the pipelined MTP decode runs a token on
  both parts and costs the slower part: at 24 the planner's 55.9 / 57.4 ms are balanced, at 27 CUDA0
  becomes the pacer. The ladder understates this (-6 %) because its decode is short; the interleaved
  52K probe is the honest number.

**Verdict: auto `24` stays for now** - the split is a ~1:1 pp/tg trade here (unlike the DS4 lane, where
the split was pure pp). Revisit after the pp-only knobs (chunk, prefill loan) and the decode-fetch knobs
(RAM tier, promotions, CPU lanes), which may move the balance.

## A5 - prefill chunk: 16K kept, 32K rejected

`--prefill 16384` (auto caps a split at 8192) plus `MAYA_GLM_PREFILL_MB=6144` so the pool can lend it.
The loan is native in this engine (chunk buffers overlay expert slots between prompts), so there is no
DS4_CHUNK_GFX11-style resident buffer to pay for - the cost is only a smaller resident set *during* a
prompt. Full ladder, 40/85 %, 1 rep:

| arm | pp 40 % | pp 85 % | tg 40/85 % | min free monitor/other | MemAvailable min |
|---|---:|---:|---:|---:|---:|
| A3b base, 8K (auto) | 775.7 | 763.0 | 19.2 / 18.5 | 556 / 338 | 11.8 GiB |
| **A5, 16K** | **902.9** | **939.1** | 19.0 / 18.4 | 755 / 336 | 10.4 GiB |
| A5b, 32K | 918.4 | 962.4 | 18.3 / 18.5 | 742 / 325 | **7.7 GiB, 1.4 GB swap** |

- 16K vs 8K: **+16.4 % pp at 40 %, +23.1 % at 85 %**, tg untouched, headroom untouched. The per-chunk
  prefill stages balance (CUDA0 16.4 s / CUDA1 17.0 s on a 16K chunk, against 12.8 / 16.9 at 8K), i.e.
  half the chunk hand-offs and half the passes over the streamed experts.
- 16K vs 8K on **short prompts is neutral**: the 52K fixed-prompt probe (3 cold segments, cache_n 0)
  measures 660.6 t/s at 8K against **654.0 t/s at 16K (-1.0 %)**. The win is a long-prompt effect (the
  52K prefill fits the same expert sets either way).
- 32K adds only +1.7 / +2.5 % over 16K and costs **2.7 GiB of MemAvailable** plus ~1.4 GB of swap-out
  (the pinned staging for a 32K chunk), so it is rejected.

**Kept: `--prefill 16384` + `MAYA_GLM_PREFILL_MB=6144`.** Note the pp numbers here are warm-box numbers;
a cold first ladder reads ~8 % lower (the page-cache drift documented on the DS4 lane).

## A6 - RAM tier 36 -> 40 GB: rejected (pp/page-cache trade, swaps)

```
A5 + MAYA_GLM_RAM_GB=40
```

The tier grew from 35.98 to 39.6 + 41.4 GB (4,568 + 4,703 experts warm, vs 4,136 + 4,172 at 36 GB) and
the decode stat shows the intended effect at 85 %: disk reads **12.79 -> 8.29/tok**, disk wait
**25.5 -> 16.5 ms/tok**, tg **18.4 -> 20.3**. But the pinned tier stole the page cache the prefill
streams from: pp fell **903/939 -> 852/889 (-5.5 %/-5.4 %)**, `MemAvailable` dropped to 6.5 GiB and the
box **swapped ~3 GB** (SwapFree 72.6 -> 69.6 GiB). The monitor/other floors also tightened to 718/301 MiB.
The RAM tier is a page-cache-vs-slots trade on a 62 GiB host; **36 GB is the balance point** here. Do not
raise it without more host RAM (or a dedicated runner).

## A7 - decode-fetch and speculation knobs: all rejected

Measured on the A5 base (16K chunk). The long ladder's first level is cold-tier contaminated (it runs
right after load), so tg-only knobs were screened on the interleaved 52K decode probe instead (4 x 256
cached decodes, cache_n 0 on the warm-up, alternating with the base; session spread +-5 %, so only
repeatable deltas count).

| arm | knob | probe tg52 | ladder tg 40/85 | verdict |
|---|---|---:|---:|---|
| A5 base | - | 25.18 / 25.32 / 25.45 / 25.52 / 25.50 / 24.60 | 19.0 / 18.4 | control spread +-5 % |
| A7 | `MAYA_GLM_PROMOTE_MIN=6` | 23.75 / 23.45 | 17.3 / 20.0 | **rejected**: -7 % on the probe; the promotions cut (22.3 -> 9.2/tok) are useful work, not churn |

| A9 | `MAYA_GLM_SPEC_CANCEL=1 SPEC_SAMPLE=1` | 24.45 / 25.57 (A/B/A/B vs 25.52/25.50/24.60) | - | neutral here (upstream's +5.3 % was an NVIDIA 3090+3060 pair) |

The promotion knobs are the counter-intuitive one: `PROMOTE_MIN=6` reduces PCIe copies but lowers the
VRAM hit rate, and the miss path (RAM tier / CPU lane) costs more than the copy it saves on this pair.

## A11 - decode take-two kernels kept, A12 rejected

```
A5 + MAYA_GLM_MLA_ATTN2=h64lvc MAYA_GLM_DSA_SCORE2=rl2b4
```

Both are the engine's bit-exact "take-two" kernels for the F32 decode attention: MLA_MMA cannot run on
HIP (compiled out), so gfx1100 runs the F32 split attention and the sparse indexer on their original
kernels. The engine logged both on both GPUs (`glm mla split attention: CUDA<n> on the take-two kernels
h64lvc`, `glm dsa scores: ... rl2b4`).

| arm | pp 40/85 % | tg 40/85 % | tg52 probe (A/B/A/B) |
|---|---:|---:|---:|
| A5 base | 902.9 / 939.1 | 19.0 / 18.4 | 24.73 / 25.70 |
| **A11 take-two** | 901.3 / 934.0 | **19.9 / 20.3** | **24.98 / 26.02** (+1.0 %/+1.2 %) |

pp unchanged (a prompt's windows keep the original kernels, by design), the 52K probe is a consistent
+1 %, the long-context ladder +5 / +10 %. The gain grows with context exactly as an attention/indexer

`MAYA_GLM_MV_RDNA=1` (A12, dense GEMVs on the RDNA3 kernel): pp 903.0 / 934.6, tg 19.3 / 18.8 - flat,
the dense GEMVs are not a bottleneck here. Not kept.

## Headroom target (met, including a picture turn)

Sampled every 5 s over the whole 4-rep ladder, sysfs `mem_info_vram_used` (card1 = monitor / HIP CUDA0,
card0 = other / CUDA1): **min free 736 MiB monitor (target >=500), 321 MiB other (target >=300)**.
`MemAvailable` min 10.3 GiB, swap flat (72.5 GiB). The 6/6 functional gates then ran with the sampler
live, including the 420x420 red/blue picture: the floor stayed **736 / 321** - the vision encoder's
2.72 GB lend comes out of the expert pool, not out of the reserve. Clean `docker stop -t 120`: VRAM back
to 436 / 28 MiB (desktop levels) in a few seconds.

Gates: `SMOKE-OK`; `get_weather` -> `{"city":"Paris"}`; `reasoning_effort: none` -> `42`; first five
primes; a fenced `sum_list`; the picture -> "the left half is red and the right half is blue."

The rule to re-check after desktop changes: **min free monitor ~= RESERVE_MB - 760 MiB** (measured
736-757 across the later arms; the 760 includes the desktop's ~460 MiB), **min free other ~=
RESERVE_LATER_MB - 380 MiB** (321-345 measured). Every ~100 MiB the desktop grows costs ~100 MiB of
floor or ~12 experts of pool; 1500/700 keeps ~240/20 MiB of margin over the targets.

## Do not repeat (on this model/pair/engine 1.1.53)

- **A manual layer split**: moving layers to the monitor card buys pp (+11.6 % at 27/18) but costs 6-13 %
  tg - the pipelined MTP decode costs the slower part, and 24/21 is decode-balanced. The split is a
  ~1:1 trade here, unlike the DS4 lane. Re-check only if the decode path changes (e.g. no MTP).
- **DFlash2 on gfx1100**: -35 % tg, accept 0.71, and it takes the head card's pool. Upstream does not
  offer it on this arch for a reason.
- **`MAYA_GLM_PROMOTE_MIN=6`**: -7 % tg; the promotions are useful work on this tiering.
- **`MAYA_GLM_SPEC_WIN=1`** (-10 %; depth-1 acceptance is only ~76-80 %), **`MAYA_GLM_GU22_TUNED=1`**
  (bit-exact but invisible behind the fetch bound), **`MAYA_GLM_MV_RDNA=1`**, **per-card CPU lanes**,
  **`SPEC_CANCEL`+`SPEC_SAMPLE`** (neutral here).
- **`MAYA_GLM_RAM_GB=40`**: +5 % tg at 85 % but -5 % pp and ~3 GB of swap on the 62 GiB host.
- **32K prefill chunk**: +2 % pp over 16K for 2.7 GiB of MemAvailable and 1.4 GB swap.
- **Reading the ladder's first level as a steady-state number**: it runs right after load, so its tg is
  cold-tier contaminated by up to 10 % (the 40 % tg is the same in both reps because the tier warms
  inside rep 1). Use the 85 % level or an interleaved 52K decode probe for tg comparisons.

## Context cap 512k -> 384k: not a speed lever (measured 2026-11-06)

Started the kept config with `--max-context 393216` and compared the load accounting; only the
per-position buffers scale with the cap:

| at load | 512k | 384k |
|---|---:|---:|
| state/KV in VRAM, CUDA0 / CUDA1 | 0.69 / 0.68 GB | 0.59 / 0.58 GB |
| pinned latent cache, per card | 3.22 GB | 2.42 GB |
| expert pool CUDA0 | 18.03 GB, 2,230 | 18.02 GB, 2,229 |
| expert pool CUDA1 | 18.82 GB, 2,287 | 18.91 GB, 2,298 |
| experts in VRAM | 4,517 | **4,527 (+10, +0.2 %)** |

The 0.1 GB a card that the smaller state frees buys 10 experts (slot rounding eats most of it), and the
1.6 GB of freed pinned RAM goes to the page cache (perhaps ~1 % fewer disk misses). For the *same actual
context* pp and tg are otherwise unchanged - per-token compute depends on the sequence length, not the
cap; pp is already flat across context on this lane. A benchmark at 85 % of a smaller cap looks faster
(334K vs 446K of prompt) only because the prompt is shorter. **Not worth 128k of usable context**; if
more speed is wanted, the levers are host RAM and the pp/tg split trade, not the cap.

## RAM tier 36 -> 32 / 30 GB: the host-RAM relief trade (measured 2026-11-06)

The lane pins 36 GB of experts + ~6.4 GB of KV, so `MemAvailable` sits at ~10 GiB during a run. Same
session, 40/85 % ladder, 1 rep, kept config otherwise:

| `MAYA_GLM_RAM_GB` | pp 40/85 % | tg 40/85 % | disk reads 85 % | disk wait 85 % | MemAvailable min | swap |
|---|---:|---:|---:|---:|---:|---:|
| 36 (kept) | 904.0 / 937.2 | 18.6 / 20.0 | 11.2/tok | 22.8 ms | 10.1 GiB | flat |
| 32 | 900.6 / 943.2 | 18.6 / 19.5 | 13.9/tok | 28.5 ms | 14.1 GiB | flat |
| 30 | 901.0 / 932.0 | 17.4 / 19.3 | 15.0/tok | 30.6 ms | 16.2 GiB | flat |

pp is unchanged (+-1 %), tg loses **~2.5 % at 32 GB and ~3.5-4 % at 30 GB** at 85 %; the freed pinned
RAM becomes page cache, so the extra streaming is largely absorbed (disk reads rise 11 -> 14-15/tok but
the wait only 23 -> 29-31 ms). Lower tiers also warm faster (smaller pinned set), keep swap flat, and
leave the VRAM floors untouched. **32 GB is the sweet spot** if host RAM is tight: 4 GiB back for ~2.5 %
of the weak axis. The deployed config keeps 36 GB until the user chooses a lower tier.

## KV int8: a memory win, not a speed win (measured 2026-11-06)

Kept config plus `--kv int8` (the 1.1.53 image needs it explicitly; 1.1.55 defaults GLM to int8).
The engine halves the latent cache, as documented:

| | fp16 | int8 |
|---|---:|---:|
| latent cache per card | 3.22 GB | **1.71 GB** (544 B/pos/layer) |
| KV window in VRAM per card | 0.20 GB | **0.11 GB** |
| state/KV in VRAM per card | 0.69 / 0.68 GB | 0.60 / 0.59 GB |
| experts in VRAM | ~4,516 | **4,527 (+11)** |
| `MemAvailable` min | 10.0 GiB | **13.0 GiB** |
| swap | flat | flat |

Speed: **pp identical** (901.8/932.2 -> 902.5/934.2), tg neutral - ladder 19.1/14.8 vs 19.7/21.0 (the
fp16 85 % sample was an outlier), and the 52K interleaved probe gives fp16 25.02/25.12/25.88 against
int8 22.70/26.08/24.82/25.05 (means 25.3 vs 24.7, i.e. within +-3 %; int8 had one slow session). The
freed 3 GiB of pinned RAM goes to page cache and the +11 experts are 0.2 % of the VRAM set, so there is
no real speed lever here - but int8 is a **better way to get host RAM back than cutting the tier**: 3 GiB
for ~0 % tg, against 2.5 % for the 36 -> 32 GB tier cut (and the two combine to ~7 GiB back).

Deployment note: after the maya 1.1.55 upgrade (TODO.md) a GLM config without `--kv` runs **int8**; the
lane's `--kv` must be made explicit either way. **Deployed 2026-11-06** at the user's request (`--kv int8`
in the lane config; the production `<pack>/slots` were cleared first because the slot identity does not
record the KV format). The quality check is the user's separate test; the revert is `--kv fp16` plus a
slot clear.

# 20261107 MTP on/off: dropping the drafter is -19 % tg (rejected)

Question: the DeepSeek lane reaches 26.5-27.5 tg with no drafter; would GLM without the NextN MTP block be
faster (its 173 MB of VRAM and the draft layer going back to the expert pool) or slower? Screen: 1 rep, 40 % of
512k only (the expected effect was large enough that the noisy first level suffices).

Method: the established tune-tree arms (`/mnt/unenc-xfs/maya/glm53f-iq2s-derisked-tune`, pack refreshed from
the production #861-repacked pack, slots empty), 1.1.56 image, port 10110, llama-swap stopped, interleaved
**A (deployed) -> B (`MAYA_GLM_NO_MTP=1`) -> A2 (control)**, `run_longctx.py --in-pcts 40 --out-pct 1 --reps 1`,
`cache_n 0`, ~209.4K prompt / 5,242 output tokens. Configs: `tune/glm-arm-configs/AB-{A-mtp,B-nomtp}`; results:
`tune/results/AB-{A-mtp,B-nomtp}-l40-r1.{json,log}`.

| arm | pp t/s | tg t/s | accept | split | experts in VRAM | min free monitor/other |
|---|---:|---:|---:|---|---:|---|
| A (MTP, deployed) | 898.9 | 18.90 | 0.752 | [0,24)/[24,45)+MTP | 2,265 + 2,304 = 4,569 | 436 / 273 MiB |
| A2 (control re-run) | 902.7 | 18.70 | 0.762 | same | same | 438 / 275 MiB |
| **B (`NO_MTP=1`)** | **880.6** | **15.30** | - (drafts 0) | [0,23)/[23,45) | **2,301 + 2,350 = 4,651 (+82, +1.8 %)** | 440 / 275 MiB |

**Verdict: MTP stays.** B is **-18.6 % tg** (18.8 -> 15.3) for **-2.2 % pp** and +1.8 % experts: the freed VRAM
does not come close to paying for the lost drafting. MTP is worth **+23 % tg** on this lane (18.8/15.3). The
pre-registered stop rule (B <= 0.8 x A = keep MTP, no longer tests) fired; do not retry this arm on 1.1.56.

Mechanics, because the result was smaller than a strict serialization predicts:

- The engine's own planner switches models with the block: MTP says "the pipelined decode: a token costs the
  slower part" (57.3 ms predicted, 55.7/57.3 per part) and the measured stat is **53.6 ms/tok**; without MTP it
  says "a token costs the parts added" (108.5 ms predicted, 52.0/56.5) - but the measured plain decode is
  **65.4 ms/tok**, i.e. the plain path already overlaps ~40 % of the per-part times (the CPU lane / fetch overlap),
  which is why dropping the drafter costs 19 %, not the ~2x of a strictly serialized split.
- Both arms stay fetch-bound: A's decode stat is `53.6 ms/tok | vram hit 72.9 % | ram 13.8/tok | disk 14.6
  reads/tok, 30.6 ms/tok | promotions 24.4/tok | cpu lane 75.2/tok in 27.8 ms`. The MTP block is not the
  constraint and its 173 MB is not the lever.
- The DS4 comparison does not transfer: there the drafter (DSpark, 8 GB) was rejected because it **evicted ~7 GB
  of experts** (77-78 % acceptance, tg -6/-11 %). GLM's NextN block is 173 MB and costs no pool. DS4's 26.5-27.5
  drafterless is a per-layer-cost story (its parts are ~18 ms each, so the serialized plain path is already
  fast), not evidence that drafters hurt.
- Side observation: without MTP the planner's cost model is "parts added", so tg is split-invariant and the
  pp-favoring split (27, +11.6 % pp) would be nearly free in tg - but that whole config is already 19 % down on
  tg, the lane's weak axis, so it is not a trade to take. Revisit only if the plain decode ever gains
  cross-token overlap without a drafter (then the 173 MB block is pure cost).
