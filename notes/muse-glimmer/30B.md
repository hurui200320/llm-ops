# 20261001 Four-slot host-memory and cache measurements

Preserve four slots with 131072 tokens each (`--ctx-size 524288`), F16 target
and draft K/V caches, ubatch 2048, GPU vision projector and DFlash depth 2.
No KV-cache quantization was tested. Both the target and the five-layer DFlash
GGUF use sliding-window attention; the draft's window is 2048 tokens.

Baseline `b11096-c550d2f60`: populate all four slots sequentially with 111493
tokens of synthetic Python source per slot, then append 20 review turns per
slot. Cold prefill was approximately 938-942 t/s. At checkpoint saturation,
median one-token appended-turn latency was 5.616 s; a simultaneous cached
request to each slot took about 10.627 s per request. Recent-history edits took
5.39-5.76 s, reusing 111958 tokens and processing only 60. A separate single-slot
128-token decode was 33.25 t/s.

Checkpoints were **118.048 MiB each**, including target and draft partial state.
The cap of 32 is per slot, so four slots can retain up to 128. Maximum anonymous
memory was 24.39 GiB; cgroup memory peaked at 45.72 GiB, including 21.28 GiB of
file cache. No swap or OOM events occurred in this unconstrained baseline.

With private/non-unified KV buffers, idle-slot copying does not free useful
VRAM capacity. The baseline repeatedly saved idle slots into the RAM prompt
cache, whose individual entries reached approximately 4.5-5.0 GiB including
checkpoint copies. Disabling eager idle-slot copying is distinct from disabling
in-slot prefix reuse or the saved-prompt cache used when a slot is actually
overwritten.

### Same-image A/B: disable eager idle-slot copies

Repeating the same workload on `b11096-c550d2f60` with
`--no-cache-idle-slots --memory 32g --memory-swap 32g`, while retaining
`--cache-ram 8192 --ctx-checkpoints 32`, gave:

| Measurement | Original | No eager idle copies |
| --- | ---: | ---: |
| Median appended-turn latency (80 requests) | 5.616 s | 0.684 s |
| Median simultaneous cached-request latency (4 requests) | 10.627 s | 0.647 s |
| Median recent-edit latency (4 requests) | 5.547 s | 0.809 s |
| Single-slot 128-token decode | 33.25 t/s | 33.06 t/s |
| Maximum anonymous host memory | 24.39 GiB | 19.42 GiB |

Cold prefill remained approximately 926-941 t/s. There were no RAM prompt-cache
entries in this four-workspace test after disabling eager copies, whereas the
baseline logged 235 cache-state updates. All four VRAM-resident prefixes still
worked. The Docker limit reclaimed file cache at 32 GiB; `memory.events:max`
increased, but swap remained zero and both OOM counters remained zero. Reaching
the cgroup limit with reclaimable file cache is not itself an OOM.

This is a large reduction in between-turn overhead, not an 8x increase in token
generation speed. The two runs also differ in their Docker memory cap, but the
unchanged compute timings and disappearance of eager cache entries identify
idle-slot copying as the main avoidable request cost.

### New-image validation and final settings

`b11312-0c1e57098`, with eager idle copying disabled, completed the same four-slot
111493-token/20-turn workload: median appended latency 0.674 s, simultaneous
cached-request latency about 0.600 s, recent-edit median 0.775 s, and single-slot
128-token decode 34.52 t/s. Cold prefill was 922-929 t/s. Maximum anonymous RAM
was 20.08 GiB, cgroup peak 28.93 GiB in this run, and swap/OOM counters stayed zero.
Different amounts of charged file cache explain some total-memory differences
between runs; do not interpret them as image-level allocation improvements.

A separate simultaneous long-context test generated 128 tokens on each of four
slots at roughly 111.6K context: 20.98-23.04 t/s per slot, 7.08-7.50 s per request,
with no swap or OOM. Concurrent cold prefills took 135-480 s including scheduling;
the sum of their long-prefill workload was not accelerated by the cache change.

Plain/streaming tool loops, strict JSON-schema output and synthetic image input
passed. The new image includes the Muse JSON-schema fix
[#29615](https://github.com/ggml-org/llama.cpp/pull/29615), failed-state-restore
cleanup [#27530](https://github.com/ggml-org/llama.cpp/pull/27530), and speculative
layer-input ordering [#29019](https://github.com/ggml-org/llama.cpp/pull/29019).
These are reasons to select the tested build, not claims of a general speedup.

Final cache flags remain `--cache-ram 8192 --ctx-checkpoints 32
--checkpoint-min-step 8192 --no-cache-idle-slots`, with the 32 GiB/no-swap Docker
limit. The four 128K private slots, F16 K/V precision and DFlash settings are
unchanged. Normal logging is `-lv 3`; the ROCm image is pinned to its tested digest.

Disabling eager idle copies does not disable saved-prompt restoration on actual
slot replacement. A separate 31.5K-token workspace-switch test saved a
1938.409 MiB state; returning reused 31526 tokens, processed five and took
0.547 s, versus 32.84 s for its initial cold prefill. This test pinned one slot
to force replacement even though other Muse slots were available. No swap or
OOM occurred.

All four smoke checks passed again through llama-swap after final config sync.
The deployed four-slot context, disabled eager idle copies, F16 defaults and
32 GiB/no-swap limits were verified, with no swap or OOM events in these checks.

# 20261002 DFlash depth comparison

Keep DFlash depth 2 and four private 128Ki slots, F16 target/draft KV, split
`26,27` and `--no-cache-idle-slots`. Tested at 111905 cold tokens/slot (85.38%).

| DFlash depth | Aggregate cold pp (t/s) | Single-active tg (t/s) | Four-way tg/request (t/s) | Peak VRAM (GiB) |
| --- | ---: | ---: | ---: | ---: |
| 2 (baseline) | 896.00 | 30.56 | 18.02-19.73 | 19.287 / 21.624 |
| 1 | 891.56 | 28.91 | 13.53-14.16 | 21.349 / 23.715 |
| 4 | 898.15 | 28.43 | 15.53-16.77 | 21.341 / 23.715 |

Depths 1 and 4 slowed decode and left only ~276 MiB on the tighter GPU.
Anonymous RAM stayed ~20 GiB; do not expand slots without validating checkpoint
RAM. Baseline cached-turn median was 1.332 s. Four-way decode remains below
25 t/s/request. Aggregate pp is total tokens / wall time, not averaged request rates.

Single synthetic runs on digest-pinned `b11312-0c1e57098`, not quality or
real-coding acceptance benchmarks. VRAM: 100-ms peaks, GPU 0 (CPU x16) / GPU 1
(chipset x4). Container swap/OOM stayed zero; host swap increased.
