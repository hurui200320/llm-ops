# 20261025 First deploy (Strata dsv41, IST-DAS 2.00 bpw, 256K)

DeepSeek-V4.1-Flash-1017 on the 2× RX 7900 XTX pair through Strata's own `strata-dsv41` engine
(gfx110x build in the llm-ops image). Model: IST-DASLab IQ2_XXS 2.00 bpw (138 GB) + the 111 GB
Engram n-gram table (read from the NVMe) + the 8 GB DSpark drafter (auto: unloaded). Context 256K
(262144); the first deploy used the default `ssd-cache=40`, the tuned lane runs 36 with
`reserve-mib=896`. Deploy record, model-file pins and the engine-discovery fix:
[notes/strata.md](../strata.md), "DeepSeek-V4.1-Flash lane (dsv41)".

Engine placement: `--tp 2` demoted to a layer split (IQ2_XXS expert blocks cannot split across two
cards), CUDA0 layers 0-20 / CUDA1 21-39, 4,353 of 15,360 experts (37.9 GB) in VRAM, 11,007
(94.9 GB) on the CPU lane, 16 threads. DSpark off (auto). At the first deploy (40 GB store) at rest
~39 GiB RAM used, ~22-23 GiB available; during the 85 % calibration prefill available fell to
~15.5 GiB with swap peaking at ~4.0 GiB (baseline 1.6 GiB). The 36 GB store frees about 4 GB for
dev work (see the ssd36 arm).

## Speed (cold prefill, through llama-swap)

+ 20% ( 52,579): pp 336.6 t/s, tg 19.0 t/s
+ 40% (105,192): pp 350.6 t/s, tg 20.7 t/s

## Speed tuning (pp first)

Goal: raise pp (350 t/s at 40 %), keep tg around 20. Method: one-shot lane containers with the
llama-swap entry's shape (`-p 127.0.0.1:10110:8080`, the entrypoint fork, same mounts/env), one arm
per container; `bench/speed/run_longctx.py --ctx 262144 --in-pcts 40,85 --out-pct 1 --reps 1` direct
on the container. The engine has no `/tokenize`, so each level pays a calibration prefill that is not
part of the measured rep (the same compensation as the Qwen 20261022 tuning). Baseline = the deployed
lane: `ssd-cache=40`, `--dspark auto` (unloaded), `--reserve-mib` 600 (default), `--prefill-chunk`
8192 (default), auto split CUDA0 [0,20] / CUDA1 [21,39].

**Arm hygiene**: `strata launch --set` extras persist in the data tree's launch preset
(`config/strata/launch-presets/docker.json`, `extra`) and the last launch state
(`state/strata/launch/docker.json`, args/env); a later arm inherits them unless overridden or the
files are removed. `split26` below ran with `--prefill-chunk 16384` inherited from `chunk16k` (pp
neutral, tg -8 %), and a first `threads=on` attempt died because the launch turns on/true/yes into a
**bare** flag (`--threads` ate `--layer-split auto`; the engine then exited on `unknown option auto`)
— use `threads=1`. `dspark=on` dies the same way (`--dspark` ate `--dspark-conf`, then `0.65` was an
unknown option) — use `dspark=1`; the engine treats any value but `off`/`none` as on. The same
applies to every dsv41 flag whose value is a word in on/true/yes (`--vision`, `--mmap-experts`): pass
a number or a non-bool word. Every arm from `threads2` on resets the two files first (backup
`.bak-<ts>`) and passes every non-default knob explicitly.

### The Qwen3.8 STRATA_SET keys do not carry over

`STRATA_SET` becomes `strata launch --set`; lowercase keys become engine argv flags (underscores to
dashes), only ALL-CAPS names become env vars (`strata_cli/launch/settings.py`, `split_setting`). The
launch only warns about a flag the engine does not list (`params.py`, `check_name`) and passes it on;
`strata-dsv41` answers any unknown option with `unknown option --x` and exit 2
(`src/dsv41/ds4_main.cpp`). A dsv41 lane given a Qwen key crash-loops.

| Qwen key | dsv41 |
|---|---|
| `kv=fp16` | no `--kv` at all (own cache format, ~17 MB / 6.5K tokens); exit 2 |
| `vram-reserve-mib=N` | the dsv41 flag is `--reserve-mib` (default 600) |
| `vram-reserve-later-mib=N` | no per-card reserve; one `--reserve-mib` for every GPU |
| `conversation-cache-mib/slots=N` | no such flags. Parking is automatic and env-tuned: `STRATA_DS4_SLOT_KEEP` (server: on), `STRATA_DS4_SLOT_GB` (server: 2), `STRATA_DS4_SLOT_CAP` (4 in RAM), `STRATA_DS4_SLOT_MIN` (1024 tok), `STRATA_DS4_SLOT_DAYS` (7), `STRATA_DS4_SLOT_DIR`, `STRATA_DS4_REUSE` |
| `resident-budget-gib=N` | Flash-Next setting, setup rejects it for deepseek41; the knob is `ssd-cache` |
| `prompt-cache-spread=on` | no analog; the prompt path is the engine's layer-major chunks plus the RAM store |
| `pipeline-windows=N`, `trim-stage-weights=on`, `spec-min-p=F` | no such flags; DSpark replaces spec decoding (`--dspark-conf`) |
| `layer-split=N` | parsed and ignored (the engine balances its own split); env `DS4_SPLIT=a,b` overrides |
| `STRATA_SCORES_THREAD=N` | env, harmless, inert (Qwen engine only) |
| `STRATA_HIPBLASLT_TABLE=on` | env, inert (`src/dsv41` has no hipBLASLt path) |

### The dsv41 speed surface (launch-side, no re-setup)

| Knob | Default | What it does |
|---|---|---|
| `ssd-cache=GB` | auto (avail-12, cap 48) | RAM store for the CPU-lane experts (the lane pins 36) |
| `ssd-policy=lru\|lfu\|lfulru` | lru | which experts the store drops |
| `cpu-threads=N` | physical cores (16 here) | CPU-lane threads |
| `prefill-chunk=N` | 8192 (`kVlRows`) | chunked prompt path; 16384 reads a prompt's experts fewer times (source comment, V100: 736 to 506 GB) but takes ~1.9 GB VRAM from the expert cache |
| `threads=on\|off` | off | a host thread per GPU enqueues its layers (hand-offs); also switches decode to threads mode |
| `reserve-mib=N` | 600 | VRAM subtracted per GPU **when sizing the expert cache at load** |
| `vram-experts=F` | 1.0 | share of the expert budget used |
| `tp=N` | 2 | tensor parallel; demoted to a layer split on IQ2_XXS |
| `dspark=on\|off\|none\|auto`, `dspark-conf=F`, `dspark-block=N` | auto / 0.65 / pack's 5 | drafter (`auto` leaves it unloaded here; never `off`, it still loads) |
| `DS4_SPLIT=a,b` (env) | auto | manual trunk layer split per group (drafter with group 0) |
| `STRATA_DS4_DSPARK_CUM=F` (env) | off | cumulative draft-confidence rule |
| `DS4_STORE_THREADS=N` (env) | 8 | RAM store reader threads |

### reserve-mib is not a free-VRAM floor

Default 600: the engine's placement line reports 586 MiB free on CUDA0 and 592 on CUDA1 **at load**.
Sampled mid-prefill (40 % calibration, chunked path): `card1` (the monitor, x16) **61 MiB** free,
`card0` (x4) 262 MiB. The chunk buffers take the reserve back, so the value bounds the expert cache
at load, not the monitor card's headroom during prefills. Keeping 300-400 MiB free on the monitor
card while prefilling needs a **higher** reserve, not a lower one; quote the mid-prefill number.

### Verdicts

- **Layer 1 (ssd-cache), kept 36**: 40 -> 36 GB is performance-neutral on this workload (pp -0.5 %,
  tg -5.9 % at 85 %, inside the noise floor) and frees ~4 GB for dev work. The store prefill scales
  with the cap (~70 % of it): 3,637 hot experts / 28.2 GB at 40, 3,248 / 25.2 GB at 36. zram is not
  an extension of the store: swap-out stayed below 1 GiB across a full 40 + 85 % run and zram data
  grew ~0.1 GB, so the store and zram coexist.
- **Layer 2a (reserve-mib), 896 for the target**: free VRAM during a run is `reserve - ~530 MiB` on
  the monitor card (the desktop's ~200 MiB is in that gap) and `reserve - ~330 MiB` on the other
  card, measured at two points: 600 -> 60 / 262 MiB, 1024 -> 492 / 668 MiB (min, whole 40 + 85 %
  run). 1024 costs 54 / 47 resident experts (-0.7 %) and no measurable speed. 896 measured
  352-357 / 544-552 MiB on the later arms — inside the 300-400 MiB target on the monitor card.
- **Layer 3a (prefill-chunk), rejected at 16384**: the larger chunk halves the passes but also takes
  215 / 182 experts out of VRAM, so each card's per-chunk read set grows. At 105k tokens the stream
  reads 203 GB per card at 0.69 GB/s and compute waits 84 s of 296 s (28 %); at 220k, 431 GB at
  0.70 GB/s, waits 175 s of 619 s (28 %). Reads are a fixed ~28 % of the prefill, compute is the
  rest; the chunk trade is a wash on pp (-4.3 / -0.5 %) and costs tg (-8.5 / -6.6 %).
- **Layer 3b (DS4_SPLIT), not kept**: `19,21` (more layers on the x4 card) makes CUDA1 the slow
  stage (read wait 36 % vs 30 % on CUDA0), costs ~7 % tg and 3.4 GiB of swap, pp flat; `26,14`
  (more on the x16 card) costs 18 % pp. `20,20` is the only arm with a real pp gain: 85 % 369.1 t/s
  vs the auto cluster 350.5-354.7 (+4.1 %, confirmed 368.1 / 370.0 in two reps) because the stage
  times are balanced (85 % prefill 600.8 s vs 627.4 s; 33 / 37 % read waits). It costs ~7 % decode
  at 85 % (18.35 vs ~19.75) and tg 20 is already marginal on this box, so **auto 21/19 stays**.

### Mechanics for pp (from `src/dsv41`)

- **The layer-major cache is single-device only.** `lm_begin()` returns false when `devs.size() != 1`,
  so on the two-card lane the prompt runs chunk after chunk and every chunk re-reads the experts the
  chunk's tokens pick from the files / RAM store (`run_dev_layers`' layer cache is the single-device
  path only). That is why pp is flat across context. The issue's single-R9700 runs (185-209 t/s pp)
  are that path; its dual-card runs did not report the layer cache either. `DS4_LAYER_CACHE_MB` is
  therefore inert on this lane.
- **Compute-bound at the margin.** The verbose prompt stream reports both sides: expert bytes from
  the files at 0.69-0.70 GB/s and "the compute waited N ms for reads". That wait is 28 % of the
  prefill at both 105k and 220k, so the remaining 72 % is GPU compute (streamed-expert GEMMs /
  hand-offs) — the CPU lane does ~0 % of the prefill experts. No launch knob moved pp beyond noise;
  the split must stay auto and the chunk at its default.
- **The CPU lane does ~0 % of the experts during prefill.** The engine's own serve line for the long
  reps says `CPU lane 0.0-0.2 % of the experts` (105k and 220k): the chunked prompt path streams and
  computes every expert on the GPUs. `--cpu-threads` and the CPU topology are decode-only concerns;
  pp is GPU-bound. That is also why the split has to balance GPU work per stage — auto 21/19 does,
  26/14 does not.
- **CPU lane on Linux**: one thread per physical core (16 here = 8 P + 8 E on the i7-13700K);
  `--cpu-threads` can only reduce that, `DS4_CPU_SMT` is Windows-only. MXFP4 rows pick `avxvnni`
  (222 us vs avx2 254 us; logged with `--verbose`). None of these move pp (decode-only).

### Final lane set (kept)

`STRATA_SET="ssd-cache=36 reserve-mib=896"` — `--dspark auto` (unloaded), `--prefill-chunk` 8192,
threads off, auto layer split (CUDA0 [0,20] / CUDA1 [21,39] + head). Measured on the clean preset:
40 % pp/tg 364.8 / 19.3, 85 % 354.7 / 19.8; 2,218 / 2,064 experts in VRAM; min free 352 / 552 MiB;
pswpout +0.02 GiB. The balanced `DS4_SPLIT=20,20` reaches 369.1 pp (+4.1 %) at 85 % but costs ~7 %
decode there (18.4) — tg 20 is already marginal on this box, so it is **not kept**. The exact lane
command was validated on 2026-10-25: engine argv `--dspark auto --dspark-conf 0.65 --tp 2
--ssd-cache 36 --reserve-mib 896 --layer-split auto`, environment `DS4_SPLIT` unset, placement
CUDA0 [0,20] / CUDA1 [21,39]+head.

pp ceiling: ~350-355 t/s with the auto split (the balanced 20/20 reaches 369 but costs 7 % tg and is
not kept), flat across context, GPU-bound (see Mechanics). For scale, upstream issue
#3933's best long-prompt number on an R9700 + XTX pair is 166 t/s (with a 35,5 split) and 31.5 t/s
auto; this box runs ~2x that on the same engine. The AGENTS.md pp >= 1000 / tg >= 25 targets do not
apply to this model/engine on 2x 7900 XTX: 256k context, 2.00 bpw, and 11,007 experts outside the
GPUs during decode.

What does not work (do not repeat): the Qwen STRATA_SET keys (unknown flag -> exit 2),
`prefill-chunk 16384` (-8 % tg), `DS4_SPLIT=26,14` (-18 % pp), `19,21` (-7 % tg) and `20,20`
(+4.1 % pp but -7 % tg at 85 %, tg is already marginal), `threads=1` (neutral), `dspark=1`
(-6/-11 % tg despite 77-78 % acceptance). Launch-layer gotchas: `threads=on` / `dspark=on`
become bare flags and eat the next option (use `1`), and `--set` extras persist in the launch
preset/state, so a test arm leaks into the next start unless they are reset (the final validation
reset them; the launch state now holds only the kept settings).

### Ceiling reference (issue #4042, 2026-10-25)

2x RTX PRO 6000 Blackwell (96 GB each, 192 GB VRAM), Threadripper 24C, 256 GB DDR5, IQ2_XS (2.25 bpw),
all 15,360 experts resident ("zero CPU-offloaded experts"), `DS4_SPLIT=19,21`: fresh prefill 1,395
(4K) / 2,299 (32K) / 2,405-2,457 t/s (131k-324k), decode ~98-116 t/s. That is the all-resident
ceiling: ~6.6x this box's pp and ~5x its tg, bought with 4x the VRAM. It is not a config to copy: the
split's +9-12 % on 16-32K prefills came from getting the last stranded experts into VRAM, impossible
here (11,007 experts outside the GPUs). The one transferable idea, a manual split, is tested as
`DS4_SPLIT=19,21` and `20,20` (see the arms table).

# 20261026 llama.cpp expert-cache experiment (shelved)

Question: does the MoE expert cache (`--moe-cache-mib`; PRs #29887 / #30112 / #30637, 2026-10-07..19)
make llama.cpp competitive with the tuned Strata lane (415-439 pp / 22.8 tg at 256K)?

The ISTA-DASLab 2.00 bpw set does not load in llama.cpp as shipped, so it was first repacked byte-exactly
into a 5-shard GGUF (248.83 GB, 1,003 tensors; every copied tensor byte-compared against the source). The
repack is mechanical (32-byte tensor padding plus two metadata fixes) and does not change the verdict, so
the process is not repeated here. Engine under test: llama.cpp `b11889-1-ga07421535`, ROCm full build for
gfx1100.

## Load and placement

`llama-server ... -cmoe -ngl 99 --moe-cache-mib 24000 -b 8192 -ub 8192 -c 32768 -lm mmap --lazy-mode on
-fa on --fit off`: loads in ~40-55 s from a warm page cache, `offloaded 41/41 layers to GPU`, KV at 32K is
~470 MiB (330 MiB K f16 + 60 + 80; V stays 0 — the dsv41 attention is MLA-style). The cache is built
**per layout group and per device** (`src/llama-moe-cache.cpp`): at 24 GB it holds 18.8-19.1 % of each
group's host experts; at 4 GB, 3.1 %. Misses are CPU-staged host→device copies, and the cache disables
pipeline parallelism (`llama-context.cpp:533`).

² The 4K prefill had not finished after 4 min (stop watch; reps were aborted).
³ 34-token warmup prefill, warm page cache.

The same 34-token warmup prefill measured 1.63 t/s (warm page cache) and 0.27 t/s (cold) on the cache
config — a 6× spread from page-cache state alone. No full 262K ladder was run: after the 4K probes both
configs were an order of magnitude off on the *favourable* end, and the mechanism below fixes the outcome.

## Why (measured)

+ Not a swap/RAM problem: the container's cgroup shows anon 1.28 GiB, memory.current 2.3 GiB, swap 276 MB;
  the host's zram holds 3 GiB for other workloads. `docker stats` reporting tens of GB is page cache
  charged to the cgroup.
+ It is major page faults over the 249 GB file: 8.0M faults (~32 GB) in ~20 min, ~125k faults (~49 MiB/s
  of 4 KiB faults) while prefilling. 62 GiB host RAM (56 GiB page cache) cannot hold the 138 GB backbone,
  and a decode token touches ~240 experts (~2.4 GB) pseudo-randomly.
+ The Strata engine wins on a tier llama.cpp does not have: 4,353 profile-placed experts in VRAM plus the
  pinned 36 GB hot-expert RAM store, so most per-token traffic is DRAM. The llama.cpp cache covers only
  19 % at 24 GB and its miss path adds copies instead of removing reads.

## Verdict

Shelve the llama.cpp DeepSeek lane; the Strata dsv41 lane stays the only viable one. Best llama.cpp numbers
are ~6-9× below the Strata lane on pp and >14× on tg, and the gap is structural (RAM/VRAM tiering +
hotness placement), not a knob. The repacked set remains the only way to run this quant in llama.cpp
(including its vision path, though vision was not validated here). Revisit if llama.cpp gains a pinned host
expert cache / hotness profile, if IST-DASLab ships a llama.cpp-native upload, or if the box gets more
RAM/VRAM. Do not repeat `-cmoe` CPU compute, `--moe-cache-mib` at 24 GB, or `-ub 8192` as a speed fix.
